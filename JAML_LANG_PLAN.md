# JAML-LANG plan — a real language service that *cannot* drift

## The one rule that killed the old attempts

KIMI's `jaml-lang` reimplemented the engine's rules in TypeScript (generated by grepping
.mjs from the WASM from the C# source). Any TS copy of the engine's semantics is **drift by
construction** — the moment the C# loader changes a key or enum, the copy is stale, and a
"valid" clause in the editor is rejected by the real loader (or worse, vice-versa, silently).

We are now past that, because the engine is **already** exported to JS as the real thing
(`Motely.Wasm/Program.cs`):

| Export | Runs | Use |
|---|---|---|
| `MotelyJaml.Validate(text)` | the real `JamlConfigLoader.TryLoad` | diagnostics |
| `MotelyJaml.ValidateLine(line)` | the real `JummyLine.TryToClause` | line-clause diagnostics |
| `MotelyJaml.FromYaml` / `CanonicalizeLine` / `CreatePlan` | real engine surface | hover/extras |

So `jaml-lang` calls `motely-wasm`, and the C# loader **is** the language server's brain.

```
any LSP editor ──LSP──▶ jaml-lang (stdio server) ──▶ motely-wasm (.NET) ──▶ real JamlConfigLoader
```

**Hard rule for this work:** the language service reimplements **zero** JAML semantics. Every
yes/no about validity comes from the engine. The only thing we *generate* is inert reference
data (key lists, enum members, docs) — and even that is emitted *by the engine, at runtime,
reflecting its own types*, never grepped or hand-listed.

---

## Two pieces, two different drift stories

### 1. Diagnostics — already drift-proof, needs only *positions*

`Validate` returns `null` or one error **string** — no line/column. A real LSP squiggles
ranges. The single engine gap to close:

- **Engine work:** make load errors carry a position. Cheapest correct version: the loader
  already knows the offending key/value and the YAML node; surface `(line, col, length)` on the
  error (e.g. a `JamlError { Message, Line, Col, Length }` returned by a new
  `MotelyJaml.Diagnose(text) -> JamlError[]`). YAML nodes from `SharpYaml.Model` carry marks —
  thread those through `ValidateKeys` / clause builders instead of throwing a bare string.
- **Fallback if marks are hard:** server-side best-effort mapping (error names a key → find that
  key's span in the doc). Acceptable for v1, but the engine-position path is the real fix and
  should be the target.
- **No new validation logic** lives in the server. It calls `Diagnose`, paints the ranges.

### 2. Completions + hover — the context-scoped vocab

This is where the old UI failed: typing in `tags:` offered a **Boss** value, because completion
fuzzy-matched the text against one giant merged enum list. **The flat "all MotelyEnums in a
parallel array" approach is the bug, not the implementation of it.**

The fix: the vocab must carry **structure** — which keys are legal in which clause, and which
enum each key's *value* is drawn from. The completion source then scopes by cursor context:

- cursor in a `tag:` value  → only `MotelyTag` members
- cursor in a `boss:` value → only `MotelyBoss` members
- cursor in a `standardCard` `suit:` value → only `MotelyStandardcardSuit`
- cursor at a clause key position inside `joker:` → only `JokerClauseKeys`

**Engine work — new export `MotelyJaml.Vocab()`** returning a structured manifest, built *in the
engine* (co-located with `JamlConfigLoader` so it reads the same `*Keys` arrays it already
defines) and reflecting the real `Motely*` enums live. Shape (not a flat array):

```jsonc
{
  "root":   { "keys": ["id","name",...,"must","should","mustNot"],
              "fields": { "deck": "MotelyDeck", "stake": "MotelyStake" } },
  "clauses": {
    "tag":     { "keys": ["tag","rolls"],            "valueEnum": "MotelyTag" },
    "boss":    { "keys": ["boss"],                   "valueEnum": "MotelyBoss" },
    "voucher": { "keys": ["voucher","rolls"],        "valueEnum": "MotelyVoucher" },
    "joker":   { "keys": [...JokerClauseKeys],
                 "fields": { "edition": "MotelyItemEdition",
                             "stickers": "MotelyJokerSticker" },
                 "valueEnum": "MotelyJoker" },
    "standardCard": { "keys": [...StandardCardKeys],
                 "fields": { "rank":"MotelyStandardcardRank","suit":"MotelyStandardcardSuit",
                             "enhancement":"MotelyItemEnhancement","seal":"MotelyItemSeal",
                             "edition":"MotelyItemEdition" } },
    // ...one entry per discriminator in ClauseKeys() switch
  },
  "sources": { "joker": [...JokerSourceKeys], "legendary": [...], "tarot": [...], ... },
  "enums":   { "MotelyTag": ["...members..."], "MotelyBoss": [...], ... }   // reflected live
}
```

The discriminator→enum map (`tag`→`MotelyTag`, etc.) is the one piece written by hand, so it is
**co-located with the `ClauseKeys()` switch** and guarded by a drift test (below). Everything
else is reflected, so adding an enum member or a key array entry shows up in the vocab for free.

### Drift guard (CI test, `Motely.Tests`)

A test that makes drift a **red build**, not a silent editor lie:

1. For every clause in `Vocab().clauses`, every listed key is accepted by the real
   `ValidateKeys` for that discriminator, and every key the loader accepts is present in the vocab
   (set equality against the `*Keys` arrays).
2. For every `valueEnum`/`fields` entry, a minimal JAML clause using one real enum member
   **loads clean** through `JamlConfigLoader.TryLoad`, and a bogus member **fails** — proving the
   vocab's enum maps to the enum the loader actually parses.
3. `Vocab().enums[E]` equals `Enum.GetNames(typeof(E))` for each referenced enum.

If someone renames `MotelyTag` or adds a clause key, this test fails until the vocab is back in
sync — and since the vocab is reflected, "back in sync" is usually automatic.

## JUMMY lines inside `must`/`should`/`mustNot`

A list entry can be a bare string (`"Eternal Blueprint in antes 1 or 2"`) routed through
`JummyLine.TryToClause`. The server detects "cursor is inside a string list item" and switches to
line mode: diagnostics via `ValidateLine`, and completion offered from the JUMMY grammar
vocabulary (joker/card names + connector words like `in antes`). Canonical form via
`CanonicalizeLine` powers a "normalize line" code action. (Line-position mapping is local to the
one string, so it's simpler than full-doc positions.)

## Deliverables & order

1. **Engine** (`Motely/` + `Motely.Wasm/`)
   - `MotelyJaml.Vocab()` export — structured, reflected, co-located with the loader.
   - `MotelyJaml.Diagnose(text)` export — error(s) with `(line,col,length)`; thread SharpYaml
     marks through the loader (or v1 best-effort fallback).
2. **Drift test** (`Motely.Tests`) — the three-part guard above. Green before any TS is written.
3. **`jaml-lang/`** — stdio LSP server (`vscode-languageserver` + `vscode-languageserver-textdocument`)
   over `motely-wasm`. Handlers: `onCompletion` (context-scoped via Vocab), `onHover`,
   `validateTextDocument` (via `Diagnose`). No JAML semantics in TS.
   - Reuse the CodeMirror-6 context-detection idea from the old UI, but *scoped by the Vocab*
     instead of fuzzy-matching one merged list — that scoping is the fix for the Boss-in-Tags bug.
4. **`jaml-lsp/`** — thin VS Code client that launches the server + `.tmLanguage.json` grammar +
   `language-configuration.json`. Salvage the **non-vocab** scaffolding from the old `jaml-lsp`
   (language-config, activation, license, icon); regenerate anything carrying vocab.
5. **Smoke**: open a `.jaml` file, type in `tags:` → only tags; type a bogus key → squiggle with
   the real loader's message; type a JUMMY line → line diagnostics.

## Non-goals (v1)
- No second grammar/parser in TS. No hand-maintained enum lists. No JSON-schema codegen.
- Formatting/rename/go-to-def deferred — diagnostics + context completions + hover first.

## Open question carried into build
- **Positions:** thread SharpYaml marks through the loader (clean, the real fix) vs. v1
  best-effort server-side span mapping. Recommend attempting marks first; fall back only if the
  loader's throw sites make it disproportionately invasive.
